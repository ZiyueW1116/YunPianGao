第一优先

DeepSeek Harness

同为 TypeScript，已找到正常结束工具轮、独立执行对象和可扩展原生摘要入口。建议以 Cordis 插件接入，并复用宿主原生服务。

完整移植候选

OpenHands → Hermes

两者都有可替换的上下文组件。OpenHands 的 SDK 会话控制更明确；Hermes 要先选定具体入口。Python 与现有 TypeScript 核心之间存在真实适配成本。

常用产品路线

Claude / Codex 等待优先

先评估任务执行、等待与接续。不能凭“支持 compact 命令”宣布预生成摘要机制已经可移植；完整支持仍受摘要提交边界约束。

以上优先级是本项目的工程判断，依据语义覆盖、接口可检查性及适配成本，不是流行度或模型能力排名。新候选均未运行模型闭环。

适配目标是宿主的真实接口。

DeepSeek 模型经 Pi 或 OpenCode 运行，使用的仍是 Pi／OpenCode 的宿主接口。这里的 DeepSeek 指官方 deepseek-ai/deepseek-harness；对其他候选也区分 SDK、CLI 插件、服务端协议与模型 API。

候选比较：两项机制分别核对

完整适配需要同时满足：① runtime 承担任务等待、超时、新输入及一次有效接续；② 空闲准备摘要，新输入使其失效，并在宿主合法压缩边界复核后提交。

“有入口／有扩展点”表示已找到文档或源码依据；“待验证”表示运行语义尚未证明。“未确认”只限定于本轮核对的接口，不等于断言宿主绝不可能提供。

依据：官方架构与 profiles

等待的建议代码流

01 · 启动绑定具体执行对象

进程优先使用 ctx.subprocess 的 handle；子 Agent 绑定一次 SubagentActivation，而不是仅凭 childId 查询“当前任务”。

02 · 等待begin → concludeTurn

注册单次等待，成功工具结果通过 exec.concludeTurn() 结束本轮。下一步 steering 仍可能继续，不能在这里提前认定宿主已经停放。

03 · 激活确认原生执行收尾

到达实际安全边界后 activate。完成早于停放时保留 ready 结果；不能在宿主正等待的 hook 中等待自己退出。

04 · 接续带身份的 inbox 输入

由 runtime 决定原因并投递。用等待 ID 关联已接纳输入；分别检查未消费与已消费消息，不能把 pending 去重当全过程幂等。

依据：ToolRunContext.concludeTurn 与成功结果标记

依据：send、followup、whenIdle 与 runMaintenance

子 Agent：优先受管 activation

startActivation 的取消信号只控制发布前阶段；返回对象提供 result 和针对该次执行的 dispose()。建议选择 delivery: "caller"，让云片糕决定何时唤醒父会话，避免原生通知和 runtime 各唤醒一次。

直接调用底层 provider.start 的 signal 会持续控制已发布执行，与“超时／新输入只结束等待”不天然相同。重等应复用 activation，不重新 resume 一个新执行。

依据：activation 与底层 provider 的不同取消契约

进程：复用原生执行与环境边界

ctx.subprocess.spawn 返回 done、输出读取和 terminate()；管理范围的完全退出另有 waitForExit()。这些比重新实现本地进程管理更合适。

宿主会过滤环境并管理进程范围；独立取消应映射其原生操作。等待超时不能触发 terminate。插件卸载、provider 卸载与宿主退出的所有权差异仍须实测。

依据：subprocess 原生服务与生命周期

摘要的建议数据流

  1. 完整回答收尾后，由核心阈值与空闲代次决定是否准备；适配层读取当前原生请求头、工具、历史范围及依赖状态，建立指纹。
  2. 沿用原生摘要生成逻辑，保存文本和对应原生 SummaryResult。后者还包含 blocks、用量及回放信息，不能只保留 Pi 风格的文本。
  3. 通过 compactNow() 进入原生 runMaintenance 边界；以 BasicCompactionEngine.summarize(input, agent, signal) 这个明确的子类扩展点，复核当前输入是否仍匹配预备结果。
  4. 资格通过后，交还原生结果，继续使用宿主的历史范围检查、替换记录和持久化；资格失效时拒绝使用旧结果。新输入默认使预备结果失效，不能被宿主“选中范围仍稳定”的较宽规则替代。

依据：唯一摘要子类扩展点与 compactNow 原生维护边界

依据：摘要后再次复核原生历史，再提交替换

最先需要验证的缺口
  • 原生 status = idle 在维护任务期间也可能成立；应按活动收尾与维护边界处理，不能照搬 idle 推断。
  • 预生成的 SummaryResult 是否仍满足原生计量、回放、摘要缩减与提交约束，尚未跑闭环。不能把“允许重写 summarize”直接等同于“缓存复用已验证”。
  • Inbox 代码检查 pending ID 重复，但这不证明消息消费后仍拒绝同 ID。一次有效恢复需要适配层复核接纳记录。
  • 实验性 plugin record 不应成为首版依赖；进程内 runtime 快照与普通请求上下文已能承载依赖，聊天记录也不能恢复执行句柄。

依据：维护活动与 whenIdle 的实现

依据：pending 输入身份检查

发行核对：源码与 @deepseek-ai/dsh-sdk-client@0.2.2-alpha.3 均可固定到本次版本；npm 的 alpha 指向它，next 为 0.2.1-rc.5，而 latest 仍是 0.0.1-rc.1。实施时必须写精确版本，不能用未限定的安装命令代替本次接口基线。

其他候选：已确认接口、建议与缺口

OpenHands Software Agent SDK

v1.59.0 · Python SDK · 源码 ccae18cb897b

完整机制的第二候选

已确认的接口事实

CondenserBase / RollingCondenser 接受只读 View，返回新 View 或 Condensation；后者由 agent loop 纳入后续历史。会话有 pause()、run()、send_message()。

适配建议 · 工程推断

原生 Condenser 可消费合格的预备摘要并交回 Condensation；任务可由独立 Conversation 执行。主会话暂停收尾后再由 runtime 恢复。

尚未证明或明确的缺口

pause 在步骤边界生效，模型调用期间不会立即暂停。需证明工具批次、用户输入、摘要提交与暂停收尾的顺序；现有 TypeScript 核心不能直接作为 Python Condenser 导入。

第一个有区分力的验收

先在独立 SDK 进程完成“工具返回 → 停放 → 子会话完成 → 一次 run”，并在等待期间提交 Condensation。确定真实跨语言调用边界后，再决定是否需要轻量 IPC。

依据：CondenserBase 契约 · pause 的实际时序 · 原生 Task Tool Set；文档定位为同步委派

Hermes Agent

v0.22.6 · Python 插件 · 源码 f0d94882e89a

摘要插件候选，等待需按入口区分

已确认的接口事实

ContextEngine 可替换，提供 compress()、on_turn_complete() 和会话生命周期。原生后台委派返回 handle。官方文档明确：API server 的异步完成只写 timeline，下一次模型轮次由客户端启动。

适配建议 · 工程推断

先用 ContextEngine 接入空闲摘要与复核消费；复用原生执行对象，再选择一个入口实现 runtime 等待和实际接续。避免并行建立第二套完成通知。

尚未证明或明确的缺口

select_context() 只替换单次请求，不能当持久压缩。on_turn_complete 是 best-effort；各入口完成通知并不等价。Python 与 TypeScript 间仍有成本，Native 子 Agent 收尾会终止其拥有的后台进程。

第一个有区分力的验收

只选 CLI 或 API 入口做首例，证明超时后任务继续、同一 handle 重等与真正新模型轮次；再验证 ContextEngine 只消费当前指纹的预备结果。

依据：ContextEngine 与只读／请求级边界 · 注册 context engine · 完成投递与进程归属

Claude Code / Agent SDK

TypeScript Agent SDK 0.3.317 · Mods 需 CLI 版本单独固定

先做等待候选，完整摘要有缺口

已确认的接口事实

SDK 有原生后台任务、task notification、backgroundTasks() 与 stopTask()。正式 PreToolUse.defer 可在非交互模式停在一个工具调用，resume 后再次进入该调用。Mods 还能在进程内访问会话与事件。

适配建议 · 工程推断

优先复用原生任务；对等待分别验证“保持工具调用挂起”与正式 defer 路径，选取满足用户新输入及等待期压缩的实现。SDK 和终端 Mods 分别作为产品入口评估。

尚未证明或明确的缺口

defer 只支持单工具调用，恢复时输入会影响原挂起调用；不应当普通成功工具结果使用。SDK PreCompact 没有现成摘要返回字段；Mods 的 session.compact 事件也只列出 skip。尚未确认合法替换预备摘要的接口。

第一个有区分力的验收

保持 streaming query 存活，先跑任务完成、超时重等与新输入，再检查同一等待期间 compact 的行为。不能通过改聊天文件补齐摘要提交。

依据：后台任务与独立停止 · 正式 defer 及单工具限制 · Mods：session.compact、session.append 和会话 API

Codex

官方 app-server 文档快照；npm CLI 0.166.0 · 本机仅查询 0.147.0 版本

以 app-server 验证等待，不先宣称完整移植

已确认的接口事实

app-server 有 thread／turn 事件、turn/start、turn/steer 和动态工具回调；command/exec 可在宿主执行策略下运行命令。thread/compact/start 触发原生压缩。

适配建议 · 工程推断

使用 app-server 保持会话，runtime 等待任务事件后经正式输入或工具输出继续；优先检查受宿主执行策略约束的 command/exec 路径。

尚未证明或明确的缺口

动态工具仍标为 experimental。公开 compact 请求未见预生成摘要载荷与提交复核回调；inject_items 是追加历史，不是压缩替换。pending 工具期间能否并行 compact、取消是否级联至独立执行，均未验证。

第一个有区分力的验收

固定实际安装的 CLI／协议版本，先跑动态工具回包与新输入竞争。task output 必须作为普通工具／会话内容进入，不能写成系统指令；不用全权限用户 shell 接口绕过执行策略。

依据：官方协议：动态工具、turn、command/exec、compact 与 inject_items · SDK 入口；与 app-server 的职责区分

Kimi Code

CLI @moonshot-ai/kimi-code@2.4.1 · 源内 SDK 0.22.0 · 源码 2c73f3f50af4

原生任务丰富，先核对发布与压缩扩展

已确认的接口事实

当前 TypeScript 源码 SDK 提供 listBackgroundTasks、输出读取、停止和 detachBackgroundTask；另有 prompt、steer、compact 和 cancelCompaction。CompactOptions 只有 instruction。

适配建议 · 工程推断

从原生 task ID 和完成事件接入 TaskSource；先验证当前 headless 后台模式何时自动接续，避免 native steer 和 runtime 双重唤醒。

尚未证明或明确的缺口

本次 npm 查询 @moonshot-ai/kimi-code-sdk 返回 404：源内 SDK 存在不代表可直接安装。同名生态另有旧 Python kimi-cli／kimi-agent-sdk，本次不混用其接口。源码 compact RPC 尚未见接纳预生成摘要的字段。

第一个有区分力的验收

先确认受支持的二进制／RPC 或打包入口，再做一个后台任务完成接续；完整摘要须先找到当前 engine 的正式替换契约，不能直接导入未承诺的内部服务。

依据：源内 SDK 名称与导出 · compact、任务与完成模式 · CompactOptions

Qwen Code

@qwen-code/sdk 0.1.27 · 官方文档仍定位为 experimental

TypeScript 等待候选，压缩需扩展契约

已确认的接口事实

SDK 支持多轮异步输入、interrupt、上下文用量和 Daemon 接入；interrupt 只结束当前轮，不关闭多轮输入流。PreCompact 可增加上下文，PostCompact 可观察已提交摘要。

适配建议 · 工程推断

先用多轮 SDK 验证正常等待与输入接续，复用已有后台能力。Daemon 和单进程 query 是不同接入面，第一版只选择其中之一。

尚未证明或明确的缺口

SDK MCP 请求默认 1 分钟超时，不能假定一个 600 秒 wait_for 调用会一直存活。PreCompact.additionalContext 不是摘要返回值，PostCompact 输出被忽略；文档中的 Function Hooks 也不是公开用户 API。

第一个有区分力的验收

先验证工具挂起、用户输入和多轮队列，再检查等待期间压缩。若需要更长 MCP 时限，必须依据实际等待契约显式设置；不能用循环唤醒规避超时。

依据：SDK、多轮输入与超时 · Hook 的输入、输出与公开范围

Google Antigravity

google-antigravity 0.1.23 · Python SDK

关注当前官方路线，完整接入仍需接口证明

已确认的接口事实

SDK 有自定义工具、子 Agent、生命周期 hooks、触发器与会话保存目录；on_compaction 文档定位为观察压缩。官方已在 2026 年公布 Gemini CLI 向 Antigravity CLI 的产品迁移。

适配建议 · 工程推断

Google 方向优先调研 Antigravity SDK；先检查原生后台触发器能否作为任务完成到实际模型轮次的桥梁，再评估 Node 核心如何接入。

尚未证明或明确的缺口

触发器存在不证明任意任务句柄可只恢复一次。尚未确认预备摘要的合法提交入口、提交前版本复核，以及挂起工具与 compact 的交错。不要把“用户套餐迁移”扩大为“所有 Gemini CLI 代码均不存在”。

第一个有区分力的验收

锁 SDK 与伴随 runtime 版本，验证一个执行 handle 的完成接续、timeout 后重等及压缩 hook 的真实可写范围；接口不足时只记录部分支持。

依据：生命周期、触发器与保存路径 · 子 Agent · Google 官方迁移说明

核心仍可复用，但不能预设端口已覆盖所有宿主

可以直接保留的业务语义

scheduler.ts 的阈值、空闲代次、摘要失效和提交资格；wait.ts 的具体执行 handle、单次 WaitRecord、deadline、先结算规则、重复通知补偿和一次接续。

TaskSource 可包裹原生进程、activation 或后台 task。原生已提供可靠执行与取消时，适配层只转换状态，不再写一套任务管理器。

必须由真实调用边界决定的部分

某些宿主结束轮次后再接续，另一些保持工具调用挂起。输入接纳、pending 工具返回、压缩屏障、独立取消和卸载清理的连接方式需要逐个验收。

原生摘要可能包含 blocks、usage 与回放凭据；当前核心只有文本和指纹。原生载荷先由适配层拥有，取得实证后再决定是否有必要调整通用端口。

语言边界也是适配成本。

核心是 TypeScript／Node.js 实现，并非可直接导入 Python 的库。OpenHands、Hermes 或 Antigravity 的 Python 扩展若要复用它，需要明确的跨进程调用边界；不能把整套业务规则重写一份后仍称作“共用核心”。当前不为候选预建 IPC 总线、Harness 基类、动态注册平台或多层工厂。

完整支持的判定线

  • 支持 MCP／ACP，只证明存在通信或工具接口；仍要单独证明任务执行、等待收尾与摘要提交。
  • 能发新 prompt，不等于已接纳消息可幂等复核；能看到 idle，不等于原生压缩或执行已结束。
  • 能追加“摘要文本”，不等于合法压缩；一次请求的上下文选择，也不等于持久历史替换。
  • 超时和用户新输入只结束本次等待；不能复用会取消底层任务的绑定关系。
  • 聊天持久化不等于任务执行可跨重启恢复。首版继续限定在进程存续期间。

下一步：先做 DeepSeek 的最小真实闭环

建议实施顺序：进程任务 → 子 Agent → runtime 等待与新输入 → 等待期间原生压缩 → 空闲预生成摘要复用 → 生命周期竞争。首个实验应尽早检验接口，不先搭建通用多 Harness 框架。

场景必须观察到的结果不能使用的替代证明
完成／失败／独立取消具体执行终态产生一次有效接续；取消为独立操作。只更新状态或只弹通知，没有实际模型轮次。
注册前完成、重复通知、完成与 deadline 同到没有漏唤醒；同一次 WaitRecord 只有一个有效恢复原因。只测正常时序或只看最终回答文本。
超时后重等、等待中新输入原任务继续；同 handle 可建立新等待；旧等待不再迟到唤醒。重新启动任务，或将停止等待映射为 terminate。
等待中 compact／准备摘要中新输入依赖可找回；接续经过原生安全边界；过期摘要不落地。只调用 compact 命令，或把摘要作为新用户消息。
接纳后回执丢失、插件 reload 与 close复核同一 ID；旧实例失效；在途创建被收尾；同步重入只启动一次清理。靠 sleep 猜宿主空闲，或把重复发送当重试。

每例使用临时项目和宿主实际支持的配置、会话、状态与缓存隔离方式；不假设 XDG。先用本机预设模型替身验证执行路径，记录模型请求数、额外唤醒、长 sleep 和完成到接续延迟；真实模型自主工具选择与摘要保真度另做评估。后续用户通过实际使用验收并反馈 bug，不承担肉眼审代码的工作。

本轮证据的终点

已完成官方资料、固定源码与包声明的静态核对，核实了版本和发布通道。没有运行任何新增 Harness 的任务闭环、模型调用或生命周期实验；本报告不新增运行支持承诺。

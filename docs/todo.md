## `wait_for`：基于任务 handle 的等待与恢复

让 Agent 表达“等这次任务结束”，由 Harness runtime 负责等待和恢复 session。减少 Agent 通过猜测时长的长 `sleep` 或反复调用模型查询状态来等待后台任务。

长工具调用和正在工作的子 Agent 都返回可等待的 handle。handle 必须能关联到具体的一次执行，并能查询或订阅其完成状态；不要求预先知道任务何时结束。

```python
call = long_tool.start(args)
await wait_for(call, timeout=600)

child = spawn_sub_session(task)
await wait_for(child, timeout=600)
```

入口可以通过 Agent 工具或 decorator 暴露，具体 API 形态需经原型验证。等待期间暂停当前 session 的推理，runtime 继续观察任务状态，并接收用户新输入。

### 待实现语义

- [ ] 统一工具调用与子 Agent 的 handle 协议，明确状态、结果、错误和一次执行的标识。
- [ ] 任务成功、失败或取消时恢复 session，并返回对应的结果或原因；注册等待前已经结束的任务应立即返回。
- [ ] 超时只结束本次等待，默认保留底层任务继续运行，handle 可以再次等待。明确区分“等待超时”和“任务失败”，任务取消使用独立操作。
- [ ] 子 Agent 或工具需要输入、授权等介入时唤醒 session，避免父子任务互相等待到超时。
- [ ] 用户新输入可以打断或调整等待；结束等待本身不隐式取消底层任务。
- [ ] 有完成事件时订阅事件，只有状态查询接口时由 runtime 轮询；机械查询不需要模型反复参与。
- [ ] 处理任务提前完成、重复通知、完成与超时同时发生、连接断开与重连；一次等待只产生一次有效恢复。
- [ ] 在 runtime 的结构化状态中保存等待关系、期限和恢复原因，使上下文压缩后仍能找回等待依赖。与压缩组合时，摘要提交仍需遵守宿主的安全替换边界。
- [ ] 长任务直接返回 handle，工具说明展示等待方式，验证模型是否会主动选择 `wait_for`。

### 原型与验收

- [ ] 先覆盖后台进程和 working subagent，在独立会话和合成任务中验证。
- [ ] 对同一批任务比较固定 `sleep`、模型反复查询和 `wait_for`，记录任务完成到 session 恢复的延迟、无理由的长 `sleep` 使用率、不必要的模型唤醒次数和 token 用量。改善幅度需实测。
- [ ] 覆盖提前完成、失败、取消、超时后再次等待、介入请求、新用户输入、重复事件及断线恢复，检查漏唤醒和重复执行。
- [ ] 在等待期间发生上下文压缩后，仍能将正确的任务结果交给对应 session 继续处理。

跨进程重启后的恢复作为后续阶段，需要额外验证持久化等待和事件重放；第一版原型先验证进程存续期间的行为。
